# 010 Ticket scope prompt, Chinese

> **语言说明.** 本仓库其余文档用英文；这一篇用中文，因为交付物是一段给中文团队用的提示词。第 5 节是成品，其余各节是它的依据、诊断与取舍记录。

The Ticket scope section is the team's own text: when a Ticket goes on, and when it stops with a draft ([004 Prompts](004-prompts.md)). This document records a Chinese rewrite grounded in published practice, and makes it the built-in default. It replaces the 22-line English text that shipped before.

## 1. 结论

这一版不靠「再多写几条规矩」，而是四件事：**一条可判定的继续标准、一张封闭的停工清单、一种结构化的草稿、一套明确的恢复规则。**

- 「继续还是停」收成一条判据：剩下的工作还能不能收成一个自包含、可评审的变更；行数、文件数、轮次都不是判据。
- 停工从「四种情形加一句散文」改成封闭清单，补上设计决定、缺权限凭据、不可逆操作、无法验证；清单之外继续做，防止代理用「可能越权」当借口早停。
- 草稿从一句「explicitly incomplete draft PR」改成可交付物：`[WIP]` 草稿 PR，加 Done / Not done / 未验证 / 为什么停 / 下一步。
- 默认替换：`prompts/team/scope.md` 现在就是这段中文，升级后新部署直接使用；已保存过提示词配置的部署需要重置本节或粘贴第 5 节。

体量：原版 22 行、2,289 字符；新版 27 行、1,180 字符。中文字符的信息密度不同，token 数不会按字符比例下降；减少的是重复、重叠和不可判定的句子。

判据没有变，还是 [000 Philosophy](000-philosophy.md) 的那一句：按影响停，不按投入停；局部变更做到可评审为止，需要设计决定就带着明确的问题停下。

## 2. 外部依据

| # | 主题 | 外部结论 | 用在新提示词的哪里 |
| --- | --- | --- | --- |
| 1 | 循环必须有出口 | Anthropic：代理可以在检查点或遇到阻塞时暂停；任务通常以完成终止，但「设置停止条件（例如最大迭代次数）以保持控制」也很常见（[Building effective agents](https://www.anthropic.com/research/building-effective-agents)） | 「停下并交草稿」的封闭清单；「没有固定轮次上限，但有失败预算」 |
| 2 | 完成要有可运行的检查 | Claude Code：没有可运行的检查时，「看起来做完了」是唯一的信号；「如果你无法验证，就不要交付」；同一问题纠正两次仍不对，应换方法或重开（[Best practices](https://code.claude.com/docs/en/best-practices)） | 「无法验证」列入停工条件；草稿要写实际跑过的检查 |
| 3 | 停工原因是可统计的 | Anthropic 对代理自主性的测量（按代理自述分类，方向性参考）：暂停原因主要是方案选择（35%）、收集诊断（21%）、澄清模糊请求（13%）、缺凭据（12%）、行动前批准（11%）；只有 0.8% 的行动不可逆；同时指出代理可能「在不该问的时候多问」（[Measuring AI agent autonomy](https://www.anthropic.com/research/measuring-agent-autonomy)） | 停工清单按这些真实原因设计；加「只有会改变改动的才问人」抑制过度提问 |
| 4 | 一次做太多会烂尾 | Anthropic 的长任务 harness 经验：代理倾向于一次做完整个应用，结果在实现中途耗尽上下文，留下半成品；对策是每次只推进一个增量，并留下可供下一次接手的产物（[Effective harnesses](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)） | 「一个自包含、可评审的变更」；草稿即交接产物 |
| 5 | 人机交接的两个触发器 | OpenAI：代理在失败时应停下并把控制权交还；触发人工介入的主要是「超过失败阈值」与「高风险、不可逆或影响大的行动」（[A practical guide to building agents](https://cdn.openai.com/business-guides-and-resources/a-practical-guide-to-building-agents.pdf)） | 失败预算；不可逆或具破坏性操作 |
| 6 | 草稿是标准产物 | GitHub Copilot coding agent 先开一个带 `[WIP]` 的草稿 PR 来跟踪并完成工作，完成后才更新标题描述、请求评审（[GitHub Blog](https://github.blog/ai-and-ml/github-copilot/github-copilot-coding-agent-101-getting-started-with-agentic-workflows-on-github)） | 草稿 PR 的形态与标题标记 |
| 7 | 一次只做一个自包含变更 | Google：合适的 CL 是「一个自包含的变更」，只解决一件事、带相关测试、评审者只看它就能理解；重构应与功能变更分开；100 行通常合适，1000 行通常过大，文件分散也算大（[Small CLs](https://google.github.io/eng-practices/review/developer/small-cls.html)） | 继续/停下的主判据；相邻问题只记录不修 |
| 8 | 失败要有预算 | Google SRE：每个请求的 retry budget 最多三次，失败三次就让错误冒泡；不要无限重试，也不重试永久错误（[Handling overload](https://sre.google/sre-book/handling-overload/)） | 「同一方法连续失败两次就换方法，三种方法都没有进展就停」 |
| 9 | 固定时间，可变范围 | Shape Up：appetite 是时间预算，不是估算；跑超了默认不给延期，这个「断路器」防止在一个需要重新思考的点上投入数倍成本；「shaped work 告诉团队在哪里停」（[Set boundaries](https://basecamp.com/shapeup/1.2-chapter-03)、[Decide when to stop](https://basecamp.com/shapeup/3.5-chapter-14)） | 失败预算耗尽就停；砍范围，不砍验证 |
| 10 | 可逆与不可逆 | Amazon 2015 股东信：不可逆的「单向门」决定要慢、要慎重；大多数可逆的「双向门」决定应快速做，信息到七成就够（[SEC](https://www.sec.gov/Archives/edgar/data/1018724/000119312516530910/d168744dex991.htm)） | 「可逆的选择自己做，信息到七成」；不可逆操作才停 |
| 11 | 规则越密越不遵守 | IFScale：500 条指令下最强模型也只有 68% 的遵循率，且明显偏向靠前的指令（[arXiv](https://arxiv.org/html/2507.11538)） | 删重复、合并同类项、把判据放在最前 |
| 12 | 位置影响遵循 | Lost in the Middle：相关信息在开头或结尾时效果最好，在中段时显著下降（[arXiv](https://arxiv.org/html/2307.03172)） | 判据放开头；停工清单靠前；恢复规则放最后 |
| 13 | 反证：过早收尾真实存在 | GPT-5.1 指南：长任务上模型可能「没有给出完整方案就提前结束」，这是可被提示词纠正的；同时要求避免不必要的追问（[OpenAI Cookbook](https://developers.openai.com/cookbook/examples/gpt-5/gpt-5-1_prompting_guide)） | 「难度、长度、文件数、红测试都不是停工理由」；只问会改变改动的问题 |

## 3. 现版诊断

现版是 `prompts/team/scope.md`（22 行，几乎每行一条规则）。它把该说的都说到了，问题在判据与结构：

| # | 症状 | 位置 | 后果 |
| --- | --- | --- | --- |
| 1 | 用行数当授权尺度 | L1–L2：把「一个模块内、几百行」作为典型规模 | 行数被误读成判据；Google 的 100/1000 行是评审可读性，不是授权边界 |
| 2 | 停工条件只有四种 | L9：破坏调用方、改模块职责、多模块协同重做、反复失败 | 缺设计决定、缺权限凭据、不可逆操作、无法验证；代理遇到未列举情形只能猜 |
| 3 | 「破坏调用方一律停」过严 | L9 | 请求明确要求破坏性变更时，它本是授权的一部分；原版没有区分「已授权」与「新决定」 |
| 4 | 「反复失败」不可判定 | L9 | 没有次数与预算：要么无限重试，要么一遇困难就早停 |
| 5 | 草稿只有一句话 | L11 | 没有标题标记、没有内容结构、不要求标出未验证项，容易把 WIP 说成 ready |
| 6 | 与内置段重复 | L13 的机器人三轮上限属于 Communication；L1、L22 与 work、delivery 重叠 | 密度越高越不遵守；重复消耗预算却不增加约束 |
| 7 | 高代价规则分散 | 停工在 L9–L13，恢复在 L15–L21 | 判据不在开头，读完 20 行才知道「什么时候可以继续」 |
| 8 | 只有反例，没有正面默认 | L3、L7 | 没有「可逆的自己定」「能查清的不问」；代理会倾向多问，或反过来「先做再说」 |

## 4. 设计原则

1. **一条判据优先于一张清单**（依据 7）：继续还是停，先问「能不能收成一个自包含、可评审的变更」，而不是问「改了多少行」。
2. **停工是闭集**（依据 1、5、10）：清单之外继续做；清单之内按影响决定停，不用难度或体量当借口。
3. **反过早停工**（依据 13、2、4）：难度、长度、文件数、红测试都不是停工理由；没有固定的调查或实现轮次上限。
4. **反过度提问**（依据 3、10）：只有答案会改变本工单要做的改动才问人；仓库里查得到的不问；可逆的技术选择自己做，信息到七成就够。
5. **失败预算化**（依据 2、8、9）：同一方法连续失败两次就换方法，三种方法都没有进展就停；砍范围，不砍验证。
6. **不可逆才停**（依据 5、10）：开分支、草稿 PR 这类双向门可以快；不可逆或具破坏性的下一步要授权，没授权就停。
7. **草稿是结构化交付**（依据 6、2）：`[WIP]` 草稿 PR，加 Done / Not done / 未验证 / 为什么停 / 下一步；没验证的不能说成通过。
8. **恢复写成状态机**（[003 Execution](003-execution.md)）：人跟帖重新评估；阻塞消失就自续；人明确说停就保持；CI 与机器人反馈不能唤醒。
9. **密度控制**（依据 11、12）：判据前置、合并同类项、删除与内置段重复的机制说明。

## 5. 新提示词

把下面整段粘贴到面板「提示词 → 工单范围」。它也是 `prompts/team/scope.md` 的默认文本。

```text
工单范围由原始请求和规则决定，不由改动大小决定。你只判断一件事：剩下的工作还能不能收成一个自包含、可评审的变更——一个最小改动，带相关测试，评审者只看它就能理解。收不了，就停下，把已完成的部分交成标了「未完成」的草稿。
### 继续做
- 实现、补数据链路、改必要的调用方、修测试和布局缺陷，只要服务于同一个变更，都属于这件事；文件数、行数、轮次都不是停工理由。
- 规格或现状不清楚时，先读原始请求、代码、测试和 git 历史。只有答案会改变本工单要做的改动才问人；否则自己选最合理的做法，并在报告里记为假设。
- 可逆的技术选择自己做，信息到七成就够了，不必请示；产品、设计或交互决定、不可逆的操作按下面的停工清单处理。
- 没有固定的调查或实现轮次上限；但同一方法连续失败两次就换方法，三种方法都没有进展就按预算耗尽停下，不要原地重试。
- 顺手发现的相邻问题只在报告里列出，不修；重构另开变更，不混进本工单。
### 停下并交草稿
出现下面任一情况，停止扩展范围，不要「先做再说」：
- 需要产品、设计或交互决定，而原始请求和规则都没有给出答案。
- 会破坏现有调用方、公共接口或模块职责，而请求没有明确要求这种变化，或没有可执行的迁移方案。
- 需要多个独立模块协同重做，超出本工单授权。
- 缺权限、凭据、环境或数据，且没有可行的替代。
- 下一步不可逆或具破坏性，而请求没有明确要求，或没有可回退的做法。
- 无法验证：测不了、看不到结果、拿不到基线，因此不能诚实地说完成。
不要用改动大小推断授权：定位一个视觉元素或改几行 CSS，都不能证明设计方向已经确定，也不能证明视觉影响小。
停下时写清具体卡点：哪个接口、哪个调用方、缺哪个前置条件，为什么局部方案不够。需要人处理时报告 blocked；主动工单在范围外或方向未定时报告 dropped，不向人追问。需要人做决定时，按 handoff 只给一个具体问题。
### 草稿长什么样
- 已完成的留在分支上，开草稿 PR（draft），标题标 [WIP]「未完成」，不写 ready。
- 写清 Done / Not done / 未验证 / 为什么停 / 下一步，附实际跑过的检查；没验证的不要说成通过。
- 没有安全可交的改动就不编造 PR，如实报告 blocked 或 dropped。
### 停下之后
- 停下不等于结束：相关的人跟帖（新线索、修正、改需求、问难度）都要重新评估一次。
- 阻塞消失或出现符合授权的可行方案，就自己继续，不要等人说「继续」。
- 纯状态问题：据实简短回答，不必重启工作；没有新信息就不动工。
- 人明确说停或等：保持停止，直到人明确解除；记下是谁、在哪儿、凭什么停的，跨跟帖、跨 worker、跨重启都保留；新的技术线索不能解除它。
- CI 与机器人反馈不能恢复已暂停的实现。
```

## 6. 与代码机制的对齐

提示词里的每条规则都有归属：能被代码强制的交给代码，团队段只写时机与偏好。

| 机制 | 由谁保证 | 新提示词怎么处理 |
| --- | --- | --- |
| `blocked` / `failed` / `dropped` 的含义 | [003 Execution](003-execution.md) 的工单阶段；`src/core/stage.ts` | 只写怎么选：需要人处理用 `blocked`，主动工单范围外或方向未定用 `dropped` |
| 主动工单的窄授权 | `mandateInstructions`（`src/executor/dsh.ts`）与 `prompts/work.md` | 不重复授权清单，只保留范围外报告 `dropped` 的处置 |
| 未完成草稿即受阻 | `prompts/work.md`：「An incomplete draft is blocked」 | 团队段定义草稿长什么样，不重复报告参数 |
| 人跟帖重新唤醒 | 003 的 blocked/failed 恢复；`src/core/assignments.ts` | 只写时机：阻塞消失自续、纯状态问题不复工 |
| 人停的持久性 | 工单与订阅的存储和恢复 | 保留「跨跟帖、跨 worker、跨重启」与「记下来源」 |
| CI 与机器人不能唤醒 | 003 的失败与恢复一节 | 保留一句，不写实现 |
| 每个机器人三轮 | Communication 段 | 从本段删除，避免两处规则互相引用 |
| 自动合并与 200 行阈值 | Delivery requirements | 本段不谈 |
| 验证手段（测试、构建、截图） | 执行环境与仓库工具 | 只要求「无法验证就停」，不规定具体命令 |

## 8. 如何验证它真的更好

不看感觉，看抽样。取改版前后各 20 个工单（含 `blocked` 与 `dropped`），人工标注：

- **该停未停**：超出授权、做进相邻问题、或返工的工单数。目标 ≤ 1/20。
- **不该停却停**：明明还能继续、却交了草稿的工单数。目标 ≤ 1/20，且必须能在草稿里找到具体卡点。
- **草稿质量**：`[WIP]`/「未完成」标记缺失、缺 Done/Not done/未验证 的草稿数。目标为 0。
- **就绪后的返工**：报告 ready 后又被发现未验证、不完整的次数。目标 ≤ 1/20。
- **提问密度**：每个工单发给人确认的问题数，中位数目标 ≤ 1；主动工单因范围或方向问题报告 `blocked` 的次数目标为 0。
- **早停信号**：因为「难」「长」「文件多」而停的工单数，目标为 0。

若「不该停却停」上升，先查是不是把难度或体量写成了停工理由；若「该停未停」上升，先查闭集里哪一条被「先做再说」绕过了。回滚用面板版本历史，或 `git revert` 这次提交。

## 9. 怎么用
