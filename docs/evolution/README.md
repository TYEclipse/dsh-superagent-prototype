# 自回归进化循环

> **本文件由自动化代理撰写，不是人类。**

**语言说明.** 本仓库的编号文档用英文；这一组记录用中文，因为提出「自回归进化」需求的是中文团队。代码标识符、命令与文件路径保留原样。

这套循环让 dsh-superagent 在没有人类逐轮重新提示的情况下，按轮次改进自己：每一轮做一次调研，找出本仓库当前最大的短板，做成一个小而可评审的变更，通过全部质量闸门，交付 PR，合并后自动发版，更新部署并重载，然后把结论写进本目录，立即开始下一轮。它不是「让代理自由修改自己」：每一轮的改动仍然走 PR、测试、覆盖率、安装验证和人工可读的记录；授权、策略与部署安全设置不在可改范围内。

## 1. 与既有循环的关系

- [docs/benchmark/evolution-loop.md](../benchmark/evolution-loop.md) 定义的是 **hermes-agent 差距发现→修复** 的队列：谁发现、谁修复、队列如何排序。它仍然有效，[docs/benchmark/gap-backlog.md](../benchmark/gap-backlog.md) 仍然是那类差距的持久队列。
- 本文件定义的是 **自进化轮次** 的合同：从调研、诊断、实现、验证、交付、发版、重载到记录。两者可以衔接——一个自进化轮可以直接消费 gap-backlog 中已经过时或仍然有效的条目——但本文件的闸门与记录要求更严格，冲突时以本文件为准。
- 旧的循环把调度器放在 DSH 宿主的 automation 里。本文件不创建、不恢复、不修改任何宿主 automation；是否定时运行由操作者决定。

## 2. 一轮的合同

每一轮是一个独立、可回滚的变更，按以下顺序执行：

1. **对账.** 读上一轮的 `docs/evolution/round-<n>.md`，核实它的 PR、合并提交、release、部署与重载是否真的发生；把过期状态改正。上一轮失败时，先按 §5 的回滚规则处理，不跳过。
2. **调研.** 做一次新的联网调研（同类 agent/harness、可靠性、评测与持续进化），记录问题、来源、日期，以及这些来源**不能**证明什么。调研不是为了凑引用，而是为了给「最大短板」一个外部参照。
3. **诊断.** 在代码、测试、部署与队列中找当前最大的短板。至少比较三个候选，按「对少占用人的注意力 / 把工作送到可验证 PR 的价值、发生频率、爆炸半径、验证成本」排序；只选一个，写清为什么不是其他候选。
4. **实现.** 一个自包含的变更：相关测试、必要的调用方、文档。不夹带相邻问题的重构。需要产品、设计或交互决定时停下，不自行发明。
5. **闸门.** 见 §3。任何闸门失败都不合并；按 §5 回滚并报告。
6. **交付.** 从本轮分支开 PR，首行写明「本消息由自动化代理撰写，不是人类」；正文写变更、原因、实际跑过的命令与结果、风险与未验证项。先自评审 diff，再开 PR。
7. **合并.** 只有 §3 全部通过、CI 绿、评审要求满足时才用部署规则点名的自动合并命令；不直接合并，不绕过保护。没有要求人工批准时也要完成自评审。
8. **发版.** 合并到 `main` 后，CI 的 release job 自动升 patch 版本、打 tag、发 GitHub release；核实 release 的 tag 指向本轮合并后的提交。
9. **部署与重载.** 把部署的 `link:` 检出更新到 release 提交，`pnpm install --frozen-lockfile && pnpm build`，按 [006 Deployment](../006-deployment.md) 的升级与重载步骤触发 HMR 重载，并用管理 API 验证 runtime、setup、parts 与检出 HEAD。重载会中断当前 Assignment；PR #19 的恢复上限保证一次重载在预算内。
10. **记录.** 写 `docs/evolution/round-<n>.md`，更新本文件的轮次索引；没有记录的一轮不算完成。
11. **下一轮.** 没有触发 §5 的停止条件时，立即开始下一轮；不等待人再说一次「继续」。

一轮只允许一个在途 PR；同一时间只允许一个进化轮。发现的新问题写进候选清单或 gap-backlog，不在本轮顺手修。

## 3. 质量闸门

一轮只有在以下全部成立时才可合并：

- **目标测试**：每个改动的行为都有对应的测试，且先证明测试在改动前失败、改动后通过（或在记录里说明为什么不能先失败）。
- **全套检查**：`pnpm check` 退出 0。它依次运行 `tsc --noEmit`、`vitest run --coverage`、`pnpm coverage:ratchet` 和 `pnpm build`。
- **覆盖率棘轮**：`coverage-baseline.json` 记录每个平台的高水位；本次覆盖率不得低于该平台的高水位减去 `--tolerance`（默认 0.10 点）。确有正当理由要降低时，用 `node scripts/coverage-ratchet.mjs --update --allow-decrease` 并在本轮记录里写明原因；不允许通过删测试、跳过测试或改断言来「通过」。
- **文档检查**：`tests/docs.spec.ts`、`tests/class-docs.spec.ts`、`tests/model-surface.spec.ts` 通过；新增测试列入 [007 Architecture](../007-architecture.md) 的 Tests 表，新增模块列入 Modules 表。
- **安装验证**：`node scripts/verify-install.mjs --dsh <path to @deepseek-ai/dsh/lib/bin.js> --receipt .artifacts/install-verification.json` 退出 0（13/13 项通过），并把 receipt 的 commit 写进本轮记录。
- **测试完整性**：没有为了过闸门而删除、跳过或弱化测试；平台相关的 skip 要记录，不能隐藏。
- **CI**：本轮 PR 的全部检查为绿；合并后 `main` 的检查也为绿。
- **部署验证**：更新 link 检出后，面板 API 的 `health.runtime.state` 为 `ready`（或预期的 setup 状态）、`setup.problem` 为空、parts 反映新构建、检出 HEAD 是 release 提交；失败时按 §5 回滚。
- **范围与安全**：没有授权、Policy、Mandate、admission、permission preset 或部署账户设置的改动；没有凭据、私密飞书内容或用户数据进入 PR。

## 4. 记录合同

`docs/evolution/round-<n>.md` 必须包含这些小节：

1. **结论**：一句话说清本轮改了什么、为什么它是当前最大短板。
2. **调研**：问题、查询、来源（带链接与日期）、这些来源能证明与不能证明什么。
3. **候选比较**：至少三个候选，按价值/频率/风险/验证成本排序，写清为什么选中的不是其他候选。
4. **现状诊断**：代码、测试、文档与部署中的具体位置（`path:line`），以及为什么现在值得改。
5. **方案**：行为、边界、与既有机制的关系、为什么放在这一层。
6. **验证**：实际跑过的命令、退出码、关键输出、覆盖率数字、安装 receipt、CI、release 与重载证据；没验证的写「未验证」。
7. **风险与限制**：固定阈值、平台差异、误报、中断、未覆盖的路径。
8. **落地与下一轮**：PR、合并提交、release、部署与重载结果；下一轮的起点与候选。

记录只写事实与可复现的命令；不要用「应该可以」代替输出。

## 5. 失败、回滚与停止

- **合并前的失败**：任何闸门失败都丢弃本轮代码分支（回到 `origin/main`），不合并、不发版、不改部署；把失败的命令、退出码和关键日志写进报告。下一轮的对账小节记录这次失败；不为了留住记录而把失败的代码合并。
- **合并后的失败**：安装验证或重载失败时，立即停止循环；把部署的 link 检出回到上一个 release 的提交，`pnpm install --frozen-lockfile && pnpm build`，再触发一次重载并确认恢复；同时开一个 revert PR 供人决定，不自动合并 revert。报告要写明坏提交、release、回滚到的提交和恢复证据。
- **停止条件**：连续两轮失败或无合并；`main` 的检查为红；在途进化 PR 超过三个；下一步需要改授权、策略或部署安全设置；需要原始请求没有给出的产品/设计决定；安装验证或重载在回滚后仍失败；本轮超出预算（默认调研 45 分钟、单轮 3 小时）。触发时记录原因并停止，不降级闸门。
- **人的停止是最终的**：人明确叫停后，循环保持停止，直到人明确解除；新的技术线索不能自行解除。
- **预算**：每轮只选一个变更、一个 PR；发现、实现、验证各只做一次主路径，同一方法连续失败两次就换方法。

## 6. 授权边界

本循环不得修改：Policy、Mandate、admission 表、permission preset、部署账户或密钥设置，以及 `docs/002-authorization.md` 定义的授权行为。不得直接合并 PR，不得在部署规则点名的命令之外开启自动合并，不得把私密飞书内容、凭据或用户数据写进 GitHub。需要这些改动时，停下来交给人。

## 7. 运行命令

```sh
pnpm check                      # 类型检查、全套测试、覆盖率棘轮、构建
pnpm coverage:update            # 覆盖率提高后抬高本平台高水位
node scripts/coverage-ratchet.mjs --update --allow-decrease   # 有理由的降低
node scripts/verify-install.mjs --dsh <path to @deepseek-ai/dsh/lib/bin.js>
pnpm release:plan               # 下一次发版会用的版本，不改文件
```

部署与重载步骤见 [006 Deployment](../006-deployment.md) 的 Upgrade 一节；本机桌面 profile 的重载触发方式见 `stateDir/work/reload-latest-plugin-*/RELOAD-NOTES.md`（不随仓库发布）。
